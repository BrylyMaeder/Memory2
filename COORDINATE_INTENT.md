# Compiled coordinate intent

Memory2 can compile a C# expression all the way to typed-column motion. The application states the update or the graph it wants; the prepared plan executes against lawful coordinates without constructing intermediate models.

This is implemented on the public `LawfulMemoryStore<TRoot>` surface. It is not a second store and it does not change the existing create, hydrate, `Save`, query, subscription, synchronization, or persistence APIs.

## Storage-native updates

```csharp
var plan = db.From<PaymentEvent>()
    .Where(x => x.Pending && x.Amount >= 10_000)
    .PrepareUpdate(x => new PaymentEvent
    {
        Attempts = x.Attempts + 1,
        Pending = false
    });

int updated = plan.Execute();
```

The member initializer is a partial update:

- assigned scalar properties change;
- omitted scalar properties remain unchanged;
- every right-hand side reads the old row, so swaps and dependent assignments are simultaneous;
- relationship properties and scalars omitted from the lawful schema are rejected during preparation;
- the selected coordinate set is captured when the source query is built;
- the prepared plan can be executed repeatedly;
- no `PaymentEvent` is constructed or hydrated.

`Update(...)` and `ExecuteUpdate(...)` execute once. `PrepareUpdate(...)` is the reusable form.

When no live query depends on the write, Memory2 compiles the complete coordinate loop. It retrieves each typed column array once, evaluates the assignments into typed locals, and performs the stores inside one loop. Capacity growth is safe because the current arrays are acquired on each execution rather than captured permanently at preparation.

When subscriptions exist, the same plan uses the exact per-coordinate path required for before/after observation. It tests only assigned columns whose values actually change, routes those columns through the existing dependency map, captures the old projection, writes the row, and publishes the new projection. The benchmark does not pretend that this observational path has the same cost as the no-subscription bulk loop.

## Storage-native graph creation

```csharp
var create = db.Set().PrepareCreate(i => new Account
{
    Name = "account-" + i,
    Active = true,
    Profile = new Profile
    {
        RiskBand = i & 7
    },
    Events = new List<AccountEvent>
    {
        new AccountEvent { Sequence = i * 2L + 1 },
        new AccountEvent { Sequence = i * 2L + 2 }
    }
});

create.Execute(ordinalStart: 0, count: 100_000);
```

The fixed owned graph is part of the expression. Memory2 verifies every owned collection cardinality during preparation, assigns root identities, calculates every descendant coordinate, and writes each scalar directly. No root, profile, event, metadata object, or collection is constructed per row at execution.

The factory ordinal is `ordinalStart + row position`. Inline `new T { ... }`, inline list initializers, and inline arrays are supported. Constructors must be parameterless, matching the lawful model contract. Values generated by application code still have their real cost: for example, concatenating a new string allocates that string even though no model graph is allocated.

Existing creation remains available:

```csharp
db.Set().Create(model);
db.Set().CreateMany(models);
```

Use those calls when the application already owns models or needs the returned tracked object. Use compiled creation when the expression is the source of the data and constructing a throwaway graph would add no value.

## Measured proof

Measured November 17, 2026 in .NET 10 Release on the benchmark machine documented in `BENCHMARKS.md`. Each process created two identical 100,000-root stores containing 600,000 connected logical objects. Update medians within each process used seven interleaved trials; the table reports medians across five independent processes.

The update selected 16,384 `MixedEvent` rows. Every trial applied 262,144 two-column updates (`Amount + 1`, `Accepted = !Accepted`). The control hydrated each event and its owned metadata, changed the POCO, and called public `Save`. The compiled path used public `PrepareUpdate` and verified identical values after every trial.

| Update measurement | Hydrate + mutate + `Save` | Compiled coordinate update | Result |
|---|---:|---:|---:|
| Median time per selected row | 425.14 ns | 1.08 ns | **407.04x paired median speedup** |
| Allocation per selected row | 148.01 B | 0 B | **148.01 B avoided** |
| Model materializations in coordinate store | — | 0 | **none** |

All five processes passed value equivalence, old-row multi-assignment semantics, exact target count, zero-allocation execution, and an additional 16,384-transition live-query check.

The creation proof compiled a complete six-object aggregate with 24 active scalar columns and three generated strings per root.

| Creation measurement | POCO graph + `CreateMany` | Compiled coordinate creation | Result |
|---|---:|---:|---:|
| Median time per aggregate root | 871.05 ns | 257.96 ns | **3.40x paired median speedup** |
| Allocation per aggregate root | 904 B | 192 B | **712 B avoided** |

The remaining 192 bytes are the three strings deliberately generated by the application expression. Root IDs, root scalars, owned-one scalars, both owned-many rows, and metadata scalars were compared between stores. Every process passed.

Reproduce the proof:

```powershell
dotnet run --project PerformanceLab/Memory2.PerformanceLab.csproj `
  --configuration Release --no-build -- `
  --coordinate-intent-proof `
  --intent-roots 100000 `
  --intent-targets 16384 `
  --intent-rounds 16 `
  --intent-trials 7
```

## Boundaries

- The 407.04x result is the measured prepared two-column update workload, not a promise that every update is 400x faster.
- Its 16,384-row working set is repeatedly updated and remains cache-resident; larger or wider writes become limited by memory bandwidth.
- Preparation and initial query selection are outside repeated execution timing.
- Active subscription observation requires before/after predicate and projection work and therefore uses a different execution path.
- Update expressions should be deterministic. A method call with side effects may be evaluated during change detection as well as writing when subscriptions are active.
- Compiled creation supports lawful fixed relationships and inline initializers; it is not a general C# object-construction interpreter.
- Omitted scalar properties use the parameterless constructor's value captured once during preparation; assign a property explicitly when its constructor default is time-varying or otherwise per-instance.
- Dynamic strings and other values produced by the expression retain their normal allocation and computation cost.
